title: "Prompt Streaming"
description: "How a pi turn becomes ACP updates, and how commands and failures resolve"
---

A prompt is one pi turn. The adapter sends the prompt as a pi RPC command and
reads pi's JSONL event stream line by line, translating each event into an ACP
session update, so the host sees assistant text, reasoning, and tool activity
as it happens rather than after the turn finishes.

## From RPC events to updates

pi RPC events map to ACP session updates for assistant text, thoughts, tool
calls, tool results, and usage counters. The full mapping table lives in
[Updates](/docs/reference/updates). pi emits a single settle event exactly
once per accepted prompt, which is the adapter's fence for finishing the turn
and committing the store mirror.

The wrapper bridge assigns each finalized assistant message a UUID before pi
persists it. The adapter publishes that durable message identity immediately,
returns it in terminal response metadata, and reuses it during history replay.
This gives persistent hosts one native correlation across live delivery,
mirror commit, process replacement, and `session/load`.

Two interactive flows are layered on top of the stream:

- **Permission requests** are surfaced as ACP permission prompts through the
  adapter's own pi bridge extension — see
  [Permissions](/docs/features/permissions).
- **User-facing questions** raised by the wrapper-owned `question` tool or an
  explicitly seeded extension dialog are forwarded through ACP elicitation,
  but only when the initialized client advertised
  elicitation support. Without it, the dialog is cancelled deterministically
  and the turn proceeds — see [Elicitation](/docs/features/elicitation).

Raw pi RPC events are not sent by default. A host opts in per session with
`_meta.pi.rawEvent.enabled`; see [Raw events](/docs/features/raw-events).

## Prompt content validation

Prompt content fails closed before the turn starts. An empty prompt (zero
content blocks) and an unsupported block type (audio or an unknown block) are
rejected with an invalid-params (`-32602`) error naming the offending field
(`prompt`). Nothing is silently dropped and nothing is forwarded to pi.

Image blocks are validated in request order, stopping on the first failure,
and every rejection is an invalid-params (`-32602`) error carrying
`{field:"prompt.image", error, index}` (plus `sizeBytes`/`maxBytes` on a limit
failure). The declared media type must be one of `image/png`, `image/jpeg`,
`image/gif`, or `image/webp`, static only: animated GIF, animated WebP, and
APNG are rejected structurally without decoding pixels. The embedded base64
data is decoded once, the sniffed format must agree with the declared type,
and the decoded bytes must fit the configured per-image and per-prompt limits
(`WithImageLimits`, 6 MiB each by default). A `uri` alongside `data` is
provenance only and is never fetched; a resource link is forwarded as text and
an embedded image resource must carry blob data.

Image support is also gated per model from pi's catalog input list: when the
selected model authoritatively lists no image input the prompt is rejected
before turn start (`unsupported_by_model`); when the catalog is silent the
prompt is forwarded and pi's provider stays authoritative.

## Slash commands

pi's RPC command inventory can describe extension commands, prompt templates,
and skills, and the adapter projects any returned entries into ACP
`available_commands` updates. A prompt whose first text block begins with
`/name` runs that command as its turn; unrecognized `/text` stays ordinary
prompt text.

The launch disables ambient extension, skill, and prompt-template discovery.
Explicit seeds under `extensions/`, `prompts/`, and `skills/**/SKILL.md` are
loaded by exact path, so their commands remain reachable. The shipped wrapper
extensions register no slash commands; a default session therefore advertises
an empty command set. Nothing is fabricated from pi's terminal-only built-ins.

## Turn resolution

A turn resolves one of three ways:

- **Success** — pi reports a terminal stop and the prompt returns an ACP
  `StopReason`.
- **Cancelled** — the host cancels; the adapter aborts the native turn and the
  prompt resolves as a successful `cancelled` response, never an error. A user
  cancel wins even if a turn timeout fires at the same instant. Abort
  acknowledgement does not complete the selected containment boundary: the
  adapter always drives that boundary before cancellation settles. On Linux
  an embedded subreaper reaps even session-detached descendants; on Windows a
  Job Object supplies the authoritative boundary. Darwin best-effort only
  reaps the direct child and observes the captured original process group
  absent; it never establishes that escaped descendants are absent. The
  normal native abort ladder ends at `agent_settled`; after containment, the
  adapter synchronously mirrors that durable aborted generation before the
  cancelled response. If escalation stops the runtime before
  `agent_settled`, no fresh generation is mirrored. The next prompt lazily
  relaunches the same logical session from the resulting committed state.
- **Failure** — a process exit, transport break, provider error, or
  `WithTurnTimeout` expiry ends the prompt with a `pi_turn_failed` JSON-RPC
  error. Timeout uses the same selected containment boundary before returning. Failures
  are never reported as a stop reason. The
  [ACP methods](/docs/reference/acp-methods) reference documents the error
  code and cause vocabulary.

Only turns that cross pi's native `agent_settled` durability fence are
mirrored. Successes, settled provider errors, and settled explicit cancels are
included. Timed-out, transport-failed, process-failed, or cancellation-
escalated partial turns that never settle are not.
