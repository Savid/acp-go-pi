---
title: "MCP"
description: "Declare MCP servers on a session and control how they reach pi"
---

pi deliberately ships no built-in MCP client — that too is left to extensions.
The adapter supplies its own pi extension, using Node built-ins and packages
supplied by the native installation, that connects the session's
declared servers, discovers their tools, and registers each one as a pi tool.
A host attaches MCP servers to a session by including them in the ACP session
request; the adapter validates the declarations before pi launches.

## Supported transports

| Transport | Support |
| --- | --- |
| stdio | Supported. |
| HTTP (streamable) | Supported, including custom headers and session-id handling. |
| SSE | Rejected at session start. |
| ACP-transport | Rejected at session start. |

Unsupported transports fail the session request with an explicit
invalid-params error before pi is launched, so a bad declaration never reaches
the CLI. Server names must be non-empty and unique within the request; they
are forwarded verbatim, never rewritten.

## Declaring servers

Build declarations with the request helpers and pass them on the session
request:

```go
servers := []acp.McpServer{
	piacp.StdioMCPServer("tools", "node", []string{"server.js"}, nil),
	piacp.HTTPMCPServer("remote", "https://example.test/mcp", nil),
}
```

## How servers reach pi

Each session's MCP config lives in its own `.acp-session/session-*` residence
under the agent directory. It is published once, left read-only, and removed
with that session. Wrapper extension sources instead live in the immutable
content-addressed cache under `WithScratchDir`. Separate residences prevent
sessions from overwriting one another's configuration; ordinary processes share
the adapter account and are not isolated from one another's reads. Protect
scratch and durable homes as described in [Security](/docs/operations/security).
The extension connects to every declared server during lifecycle establishment.
Because some hosts deliberately expose only a side-effect-free readiness
surface until an operation is authorized, the adapter rebuilds pi's fixed
extension-tool registry once more at the first user turn. Every tool then
available is registered under `mcp__<server>__<tool>`, so a provisional
readiness list cannot replace the real session tools. The same refresh runs
after `session/load`; a later native-process relaunch already occurs inside an
authorized turn and discovers the active surface directly.

Declared env vars are forwarded to stdio children and declared headers to HTTP
servers. MCP tool calls run under the same
[permission gate](/docs/features/permissions) as built-in tools, and an aborted
turn cancels an in-flight MCP call promptly. Stdio cancellation sends a
best-effort MCP cancellation notification; HTTP cancellation aborts the fetch.
Both request transports have a 60-second timeout.

A server that fails to connect at session start — an unreachable command, an
HTTP 401 — fails establishment with `pi_internal_failure`, class `native_start`.
Native refusal text is not included in that closed wire error. A startup failure
closes already-opened MCP transports.

## Scope

Forwarding is tools-only, with one fixed registry established for user turns:

- Discovery registers the first `tools/list` page; pagination is not followed.
- HTTP accepts JSON or a completed SSE response body. It does not consume
  indefinitely open event streams.
- MCP **resources** and **prompts** are not projected into the session.
- **Server-initiated requests** (sampling, server-side elicitation, roots) are
  not answered; a server that sends them will see them time out on its side.
- **Tool-list change notifications** are ignored. After the first authorized
  refresh, the tool set remains fixed for that native process.

<Note>
Plan around request/response-style MCP servers: the client answers only
responses to its own requests. Servers that depend on server-initiated MCP
traffic will not function correctly through this adapter.
</Note>
