---
title: "Elicitation"
description: "Forward pi's user-facing dialogs to clients that opt in during initialize"
---

When a pi extension needs to ask the user a question mid-turn — a confirm, an
input box, or an editor dialog — the adapter can forward it to the host as an
ACP elicitation request. The adapter loads only its own wrapper extensions;
ambient and seeded extensions are not discovered. The shipped extensions
currently raise only permission dialogs, so a default session has no
non-permission dialog producer even though the relay and capability descriptor
are available.

## Capability gating

Elicitation is only used when the client advertised elicitation support during
ACP initialize. The adapter checks that capability before sending anything, so
a client that never opted in is never handed an elicitation request it cannot
render.

| Client elicitation capability | Adapter behavior |
| --- | --- |
| Advertised | The pi dialog is forwarded as an ACP elicitation request. |
| Absent | No request is sent; the dialog is cancelled deterministically and the turn continues per pi's own logic. |

<Note>
Elicitation is not the permission channel. Tool-access approvals always use
[permission prompts](/docs/features/permissions); elicitation carries
free-form questions only.
</Note>

Because behavior depends on the client's advertised capability, test both
paths: a client that supports elicitation and one that does not.

## Route correlation

The initialize response advertises route-envelope version 1. Every emitted
form elicitation contains the owning session, current turn nonce, and exactly
one callback correlation under `_meta["acp-go.dev/route"]`, while preserving
other metadata. A pre-existing reserved key fails the callback closed.
