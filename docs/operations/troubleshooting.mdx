Each symptom below names the behavior that produces it and a local regression
test. Fake-backed tests, including `TestFakePi*` and compiled-wrapper tests,
exercise scripted RPC fixtures and prove wrapper behavior. Tests that execute
the real `pi` CLI establish native compatibility for that run; a fake fixture
does not renew native evidence.

## A concurrent prompt is rejected as busy

A pi RPC process exposes exactly one active session at a time, and this
adapter runs one RPC process per ACP session with a per-session turn capacity
of one. A `session/prompt` that arrives while a turn is active is rejected
with an invalid-request error carrying `"error": "backpressure"` and
`"limit": "session_prompt"`; it is never queued. At the native surface pi
refuses a second bare prompt while streaming and acknowledges a steer of the
active turn only after queuing it. `TestFakePiBusyRejectionAndSteerAck`
(`integration/fake_pi_protocol_test.go`) scripts those responses to pin wrapper
handling.
Wait for the active turn to settle, or cancel it, before prompting again; the
adapter does not expose pi's steering queue.

The same refusal covers two more cases where the single foreground is already
occupied. pi can begin work between prompts — the session projects it as an
agent-origin cycle and refuses a `session/prompt` until that cycle reaches its
durable boundary. A native steering or follow-up queue pi has not drained is
also work already accepted ahead of the new prompt, and is refused on the same
terms; the adapter reads only that queue's size and never its entries.

An active `session/load` or `session/resume` reads the same single foreground
from the other side. It is refused with `"limit": "session_restore"` while a
prompt is in flight, while an agent-origin cycle is open or settling, or while
the native queue is non-empty, because the session's transcript is still being
written and the stored prefix is one it has already moved past. A restore that
is admitted holds that foreground until its replay finishes, so a `session/prompt`
arriving during a replay is refused with `"limit": "session_prompt"` and any
work pi begins meanwhile is held rather than projected mid-replay.

A native record the adapter cannot place — assistant or tool output, a turn or
agent bracket, a retry or compaction pair, a settle marker, or a second
`agent_start`, all with no cycle open — is an invariant failure rather than
something to guess at. The generation is fenced and the session is poisoned;
later requests report `-32603` with
`{"error":"pi_session_poisoned","cause":"<token>"}`, where `cause` is one of
the closed structural tokens listed under
[Off-prompt internal errors](/docs/reference/acp-methods). The prose reason
never reaches the wire; it is in the adapter log. Recovering means opening a
fresh session.

## Forking a fresh session fails

Forking runs through the `_pi/session/fork` extension method, and a fork of a
session with no conversation yet fails with a structured error: pi's native
clone of an empty session reports a missing session entry, and the adapter
classifies that as an explicit rejection rather than a native crash. Complete
at least one prompt turn before forking.
`TestProviderTurnFailureAndEmptyCloneError` (`session_failure_test.go`) pins
the classification; `TestPiACPLiveForkSession`
(`integration/agent_live_test.go`, live tier) drives the real binary through
the rejected empty fork and a successful fork after a seeded turn.

## A cancel lands while a permission or elicitation dialog is open

`session/cancel` and terminal close mark the turn cancelled and resolve every pending
dialog as cancelled, and a cancelled dialog fails closed: the adapter
answers pi's native dialog — deny for a permission dialog, cancel for an
elicitation/question dialog — so the blocked tool call or question resolves
and the RPC process settles instead of waiting on an answer that never
arrives. Both dialog kinds share the same registration mechanism, so the
guarantee holds for either. A dialog that arrives after the cancel starts
already cancelled and is resolved the same way. `TestRegisterDialogCancelledTurn`
(`session_permissions_test.go`) pins that a dialog registered on a cancelled
turn begins with an already-cancelled context and leaves no pending dialog
behind.

A dialog received between dispatched prompts has no submission owner. The
adapter immediately answers it with native deny/cancel instead of publishing a
host request or leaving pi blocked. If a written permission or elicitation
request cannot be announced on the negotiated lifecycle stream, its request
context is revoked and the exact process generation is contained without
waiting for a host answer.

## Output stops but the turn stays active

pi ends every accepted prompt with exactly one `agent_settled` event, emitted
after the terminal `message_end` → `turn_end` → `agent_end` ladder and only
once no automatic retry, compaction retry, or queued continuation remains.
The adapter treats `agent_settled` as the turn-completion fence: the prompt
response and the durable session mirror wait for it, and nothing observed
after it belongs to the turn. A turn whose streamed output has stopped but
which has not returned is a turn whose process has not settled yet.
`TestFakePiPromptTurnLifecycle` (`integration/fake_pi_protocol_test.go`) pins
the event order, the exactly-once settle, and the durable session file at the
fence. A turn that never settles can be bounded with `WithTurnTimeout` — see
[Observability](/docs/operations/observability) for the resulting failure.

## The MCP tool set is stale after changing servers

The pi RPC process fixes its MCP configuration at launch: the adapter writes
MCP config into the session's private configuration residence, and
pi's extension-tool registry is established for that process. Changing a
session's MCP servers therefore means closing the session's RPC process and
relaunching it with the new declaration — there is no in-place mutation. The
adapter refreshes the registry at the first user turn and after a resume, so
a server that exposes only a provisional readiness surface until an operation
is authorized does not leave the session stuck with the readiness stub as its
tools (see [MCP](/docs/features/mcp)). `TestPiACPRuntimeMCPRefresh`
(`integration/mcp_runtime_refresh_test.go`) drives the real pi binary,
without provider credentials, through exactly this close-and-relaunch
refresh: a session established against a readiness-only surface, the real
tool surface on the first turn, and — after adapter shutdown — a resumed
session that refreshes the registry again before continuing.

## Splitting install problems from provider problems

Every pi child launches with `PI_OFFLINE=1` and answers its state probes
without provider credentials: `get_state`, `get_commands`, and
`get_session_stats` succeed on a credential-less RPC process
(`internal/pi/command.go`, `internal/pi/ordinary_process.go`). That split routes the
diagnosis:

| Observation | Conclusion |
| --- | --- |
| Session creation or its startup state probes fail | Confirm `pi` is on `PATH` and is version 0.80.6 or newer. Native startup failures carry `pi_internal_failure`, class `native_start`; adapter logs contain fixed classifications and stages. |
| Session creation and probes succeed; prompts fail with cause `provider` | Credential problem — credentials were not injected for the session (ambient shell keys are scrubbed) or the provider refused them. |

<Note>
For an explicitly authorized native probe, launch `pi --mode rpc` in a
throwaway `PI_CODING_AGENT_DIR` with a scrubbed environment. `get_state` and
`get_commands` need no provider credentials. Source inspection and ordinary
fake-backed tests can diagnose wrapper handling without launching pi.
</Note>
